O suporte da Coplan funciona em níveis. Cada nível responde uma pergunta diferente sobre o problema e entrega para o próximo o que ele precisa para continuar.

Nível 1 · onde você começa

Atendimento inicial

"O que está acontecendo, com quem e onde?"

Faz

Recebe o cliente, entende, classifica, resolve dúvidas de uso, levanta evidências, abre a OS completa, acompanha e devolve a resposta.

Ferramentas

Chat e OS do Cliente Mais, o sistema em homologação, F12 do navegador.

Precisa saber

Os produtos da Coplan, os fluxos mais comuns, o checklist e a comunicação no chat.

Nível 2

Suporte especializado

"Por que está acontecendo?"

Faz

Reproduz, levanta hipóteses, analisa dados, configurações e requisições, resolve o que é configuração e separa defeito de melhoria.

Ferramentas

F12, Swagger, Postman, registros do sistema (logs) e o ambiente de homologação.

Precisa saber

As regras de negócio do módulo, como uma API funciona, HTTP e JSON.

Nível 3

Desenvolvedor

"Como corrigir sem quebrar outra coisa?"

Faz

Acha a causa no código, corrige, testa em homologação e publica a correção em produção.

Ferramentas

O código do sistema, Git, ambientes de desenvolvimento e homologação.

Precisa saber

Programação, banco de dados e como o sistema é construído.

O que liga os três níveis é a OS

Cada nível só trabalha bem se o anterior entregou tudo. Uma OS incompleta volta para o N1, e o cliente espera mais. Uma OS completa vai direto para a solução.

O que a Coplan faz

A Coplan é uma GovTech de Cuiabá que desenvolve sistemas de gestão pública para prefeituras. Quando um município emite o IPTU, paga a folha dos servidores, presta contas ou organiza as escolas, é o sistema da Coplan que está por trás.

Produtos

Quem está do outro lado do chat

Você atende o servidor público, não o cidadão. Mas muitas vezes tem um cidadão na frente desse servidor, esperando no balcão. Quando o sistema para, a fila para.

Épocas de pico

Início do ano

IPTU e taxas do novo exercício. Muita emissão de guia.

Todo fim de mês

Fechamento da folha. Erro aqui mexe no salário de alguém.

Fim do ano

13º salário e encerramento do exercício contábil.

Prestação de contas

Envio de dados ao Tribunal de Contas. Perder o prazo pode gerar multa para o município.

Por que um erro pesa mais aqui

Prazo na lei

Vencimento de imposto, folha e prestação de contas têm data.

Dinheiro público

Cada erro mexe com dinheiro do município e pode ser auditado.

Dados pessoais

CPF, salário e endereço de cidadãos. A LGPD vale para tudo o que você copia e envia.

    O sistema faz o que foi feito para fazer, mas o cliente quer outra coisa. Vira sugestão.

    Por que olhar por trás da tela

    Um sistema web tem duas partes. A tela (o front-end) roda no navegador do usuário. O servidor (o back-end) roda nos computadores da Coplan, faz os cálculos e guarda os dados. Cada clique faz a tela mandar um pedido ao servidor e esperar a resposta.

    Quando a tela mostra "Erro inesperado", o servidor quase sempre mandou uma resposta com o motivo real. As ferramentas do desenvolvedor (DevTools) do navegador mostram essa conversa. Todo Chrome e Edge tem, e é por elas que o N1 acha o motivo.

    Como abrir

    Tecla F12

    No Chrome e no Edge, no Windows. Em alguns notebooks é Fn + F12.

    Atalho

    Ctrl + Shift + I no Windows. Cmd + Option + I no Mac.

    Botão direito

    Clique com o botão direito na página e escolha Inspecionar.

    No celular não existe F12. Se o problema é no app ou no celular do cliente, reproduza no computador em homologação.

    Cuidados com o F12
    • Nos Headers aparece Authorization ou Cookie. É a chave de acesso do usuário. Nunca copie isso para a OS, o chat ou o WhatsApp.
    • Não use "Copy as cURL" sem orientação do N2: ele leva a chave de acesso junto.
    • A resposta pode ter CPF ou salário. Leve só o que explica o erro, e só pela OS.
    • Nem todo sistema tem endereços legíveis como no exemplo. Se o nome da requisição for técnico, olhe o status e a resposta.

    O que é uma API

    API é o jeito combinado de um programa pedir coisas para outro. A tela do sistema não guarda os dados nem faz os cálculos: ela pede para o servidor, pela API, e mostra a resposta.

    TelaSalão

    Onde o cliente vê o cardápio e faz o pedido.

    APIGarçom

    Leva o pedido para a cozinha e traz a resposta.

    ServidorCozinha

    Faz o trabalho: calcula, valida, gera a guia.

    Banco de dadosDespensa

    Onde os dados ficam guardados.

    No F12 você viu o garçom voltando com uma resposta ruim. Agora vamos ler essa resposta e a documentação do cardápio.

    Swagger: o cardápio da API

    O Swagger é a documentação de uma API, em forma de página. Ele lista cada endereço, qual método usar, o que enviar e o que pode voltar, e permite testar com o botão Try it out. Quando uma API da Coplan tiver Swagger, o N2 ou a equipe do produto passa o endereço de homologação.

    Para o N1, o Swagger responde perguntas como: "a tela mandou o dado certo?" e "esse status de erro está previsto?".

    E o Postman?

    O Postman é um programa que faz o mesmo pedido da tela, só que fora do navegador. Serve para o N2 testar a API direto, sem depender da tela. É ferramenta do N2. Você aprende na trilha N2.

    Regra de ouro: se não está na OS, não aconteceu.
    • Registre durante o atendimento, não no fim do dia.
    • Escreva para quem não estava na conversa.
    • Use as palavras do cliente e acrescente os dados técnicos.
    • Cole a mensagem de erro exata, não um resumo.
    • Nada de senha nem chave de acesso. CPF e dados pessoais só no campo próprio do Cliente Mais.

    Para que serve esta trilha

    Estude depois da imersão, no seu ritmo. Você não vai fazer o trabalho do N2 amanhã. Vai entender como ele pensa, entregar OS melhores e se preparar para crescer.

    Erro ou melhoria?

    Erro

    O sistema não faz o que deveria fazer. Ex.: o botão Emitir mostra "Erro inesperado".

    Melhoria

    O sistema faz o que foi feito para fazer, mas o cliente quer outra coisa. Ex.: exportar em Excel um relatório que só sai em PDF.

    Levantar um requisito

    Requisito é a descrição do que o sistema precisa fazer. Para uma melhoria, o N2 transforma o pedido do cliente em algo que o produto consegue avaliar e o desenvolvedor consegue construir.

    1. Quem pede e para quê: qual o papel da pessoa e qual problema ela quer resolver.
    2. Como faz hoje: o caminho atual, mesmo que seja fora do sistema (planilha, papel).
    3. O que espera: o resultado, sem decidir a solução por ela.
    4. Regras: leis, prazos, cálculos envolvidos.
    5. Como saber que ficou pronto: o critério de aceite.

    História de usuário

    Como [quem], quero [o quê], para [por quê].

    "Como contadora da prefeitura, quero exportar o relatório de arrecadação em Excel, para montar a prestação de contas sem digitar os valores de novo."

    Critério de aceite

    Dado [situação], quando [ação], então [resultado].

    "Dado que estou no relatório de arrecadação, quando clico em Exportar, então recebo um arquivo .xlsx com as mesmas colunas e totais da tela."

    O método

    1. 1
      Reproduzir no mesmo cenário

      Mesmo município, mesmo dado, mesmos passos.

    2. 2
      Isolar

      Acontece só com esse usuário? Só nesse município? Só nesse navegador? Desde quando? O que mudou nesse dia: atualização, cadastro, virada de exercício?

    3. 3
      Levantar uma hipótese

      Uma explicação que dá para testar. Ex.: "falta o parâmetro de desconto de 2026".

    4. 4
      Testar a hipótese

      Pela API no Postman, comparando com outro exercício ou outro município, sempre em homologação.

    5. 5
      Concluir e registrar

      Configuração, defeito, melhoria ou uso. A conclusão e a evidência vão para a OS.

    Regras do Postman
    • Só no ambiente de homologação. Nunca em produção.
    • Nunca use chave de acesso de produção nem o login pessoal de um cliente.
    • Use a collection e o environment que a equipe te passar.
    • Postman serve para entender e evidenciar, não para corrigir dado.

    No Postman de verdade

    1. Abra a collection que a equipe compartilhou.
    2. No canto superior direito, selecione o environment Homologação.
    3. Escolha a requisição e preencha os parâmetros.
    4. Clique em Send.
    5. Compare o status e a resposta com o que o F12 mostrou.
    6. Cole o resultado na OS.

    O ciclo de uma correção

    1. 1
      Entender e reproduzir

      Lê a OS e o relato do N2 e reproduz no ambiente de desenvolvimento.

    2. 2
      Achar a causa

      Procura no código o ponto onde o comportamento diverge do esperado.

    3. 3
      Corrigir numa branch

      Faz a alteração numa cópia separada do código, sem mexer no que está funcionando.

    4. 4
      Revisão (pull request)

      Outro desenvolvedor revisa a mudança antes de ela entrar.

    5. 5
      Testar em homologação

      O caso do cliente e o que pode ter sido afetado.

    6. 6
      Publicar em produção (deploy)

      A correção entra numa versão nova do sistema, e o N2 é avisado.

    Glossário

    TermoO que é
    Código-fonteO texto que os desenvolvedores escrevem e que vira o sistema
    GitFerramenta que guarda o histórico de cada mudança no código
    CommitUma mudança salva no histórico, com uma mensagem explicando o que mudou
    BranchUma linha separada de trabalho no código, para mexer sem afetar o resto
    Pull requestO pedido para juntar a mudança ao código principal, com revisão de outra pessoa
    Desenvolvimento, homologação e produçãoOs três ambientes: onde se programa, onde se testa e onde o cliente usa
